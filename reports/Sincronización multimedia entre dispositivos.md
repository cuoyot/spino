# Synchronize SPino recordings through personal Drive

Research date: October 16, 2026. Status: owner selected personal Google Drive with no additional SPino subscription; the technical design still requires a native proof of concept and is not implemented.

Owner preference confirmed on October 16, 2026: use the user's own Google Drive rather than introduce a paid SPino storage subscription. Storage uses the user's provider allowance. The specific API, authorization flow, migration and transfer policies below remain proposed engineering choices requiring validation.

**The best fit for SPino is optional Google Drive synchronization using the REST API and the narrow `drive.file` permission, with recording files and a separate media manifest.** This preserves local recording and offline playback while using the user's existing cloud storage instead of introducing SPino accounts and a storage service. Keep the current notebook connection working and enable media separately. This recommendation assumes synchronization between one person's Android/iOS devices, potentially including the browser; sharing between different people changes the authorization design. Validate it first on two disposable native installations: authorization, discovery, interrupted transfers and playback must work before committing to rollout. A working browser demonstration or successful upload on the first device is insufficient evidence.

## Drive fits the current product better than a managed service

SPino currently delegates notebook synchronization to an OS document provider and operates without a SPino server, account system or OAuth client. Recordings remain in a separate local database. Drive REST adds Google authorization but avoids making SPino responsible for every user's media bill and account recovery. This is an architectural judgment based on the current product, rather than a claim that Drive implements synchronization automatically. ([Current cloud architecture](/Users/migue/Source/spino/docs/cloud-backup.md), [media store](/Users/migue/Source/spino/src/companion/media-store.js:4))

| Option | Main advantage | Main constraint | Fit for SPino |
| --- | --- | --- | --- |
| User's Google Drive through REST | Existing user storage; explicit upload/download APIs; no SPino storage backend | Google authorization, quota handling and a new sync engine | **Recommended first adapter**, pending native tests |
| Extend current OS provider to folders | Retains provider choice and current account model | Folder operations vary by provider; local acceptance does not prove cloud delivery | Keep for notebook sync and export; qualify individual providers before offering media |
| Private Cloudflare R2 plus backend | Low storage cost and no direct Internet egress charge | SPino must operate identity, authorization, metadata and quotas | Best storage foundation if SPino later owns the service |
| Supabase Auth, database and Storage | Integrated identity, permissions and metadata | Subscription/egress costs; Free's 50 MB file limit | Faster managed-service starting point if SPino accounts become a product requirement |

Android supports directory grants through `ACTION_OPEN_DOCUMENT_TREE`, and iOS supports directory access, but individual providers must expose the necessary capabilities. **There is no verified universal Google Drive folder-picker path here.** Extending SPino's current single-document bridge would still require binary I/O, directory operations and cross-device delivery tests. ([Android documents](https://developer.android.com/training/data-storage/shared/documents-files), [DocumentsProvider requirements](https://developer.android.com/reference/android/provider/DocumentsProvider#isChildDocument(java.lang.String,%20java.lang.String)), [Apple directory access](https://developer.apple.com/documentation/uikit/providing-access-to-directories))

Drive storage consumes the user's existing allowance: a Google Account includes 15 GB shared with Gmail and Photos. Standard Drive API use currently has no additional charge, but Google's published policy plans above-quota charges later in 2026; **do not promise a permanently free API**. ([Google storage](https://support.google.com/googleone/answer/9004014?hl=en), [Drive quotas and pricing](https://developers.google.com/workspace/drive/api/guides/limits#pricing)) For comparison, R2 Standard lists $0.015/GB-month, a 10 GB monthly storage allowance and no direct egress fee; Supabase Pro starts at $25/month with 100 GB storage, while its Free plan cannot accept a 250 MB recording. These are service components, excluding backend engineering, operations and applicable overages. ([R2 pricing](https://developers.cloudflare.com/r2/pricing/), [Supabase pricing](https://supabase.com/pricing), [file limits](https://supabase.com/docs/guides/storage/uploads/file-limits))

## Media needs its own identity and transfer pipeline

SPino's notebook JSON is limited to 60 MB, while capture stops around 250 MiB or 15 minutes. Native notebook bridges currently load complete UTF-8 documents; they expose no binary transfer API. Recordings are filtered by installation and require a local Blob, so remote metadata alone would disappear from today's viewer. Embedding recordings as base64 would enlarge them by roughly one third and retransmit unrelated media on notebook edits. **A separate binary transport is required.** ([Capture](/Users/migue/Source/spino/src/companion/media-view.js:102), [sync limits](/Users/migue/Source/spino/src/companion/cloud-sync.js:25), [Android bridge](/Users/migue/Source/spino/android/app/src/main/java/com/miguecoll/spino/CloudBackupPlugin.java:17), [iOS bridge](/Users/migue/Source/spino/plugins/cloud-backup/ios/Sources/CloudBackupPlugin/CloudBackupPlugin.swift:11))

The proposed manifest preserves each take's UUID and adds notebook scope, work/session association, title, duration, format, exact byte size, checksum and immutable object reference. Device paths, cache availability, installation provenance and queue progress remain local. Preserve original musical titles and user text. A remote recording appears with a download action; playing downloads and verifies it, while “keep offline” pins the local copy. Renaming updates metadata without uploading the recording again.

For native platforms, use persistent private files and native transfers from file handles, with bounded migration from existing Blobs. **Never send an entire 250 MB base64 payload through Capacitor.** Keep a durable queue with retries, progress and account/notebook binding; upload and verify bytes before publishing availability. Drive recommends resumable uploads for files over 5 MB and unstable networks, with authenticated range downloads available. Session expiry, retries and duplicate detection still require application logic. ([Drive uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads), [downloads](https://developers.google.com/workspace/drive/api/guides/manage-downloads))

Saving must succeed offline. Upload saved takes, retain drafts locally, and download on demand to limit disk and network use. Background scheduling requires native work: Android WorkManager supports persistent constrained tasks, while Apple's background sessions upload from files and remain subject to system scheduling. Neither establishes uninterrupted completion in every termination scenario. ([Android persistent work](https://developer.android.com/develop/background-work/background-tasks/persistent), [Apple background transfers](https://developer.apple.com/documentation/foundation/downloading-files-in-the-background))

## Link devices through authorization, not notebook identifiers

Use one Google Cloud project with platform-specific OAuth clients and `drive.file`, which Google recommends as a non-sensitive scope covering app-created or explicitly opened files. Prefer a visible SPino-created folder containing app-created media for recovery and portability. Do not assume selecting an arbitrary folder authorizes every descendant. ([Drive scopes](https://developers.google.com/workspace/drive/api/guides/api-specific-auth), [folder creation](https://developers.google.com/workspace/drive/api/guides/folder), [cross-client identity](https://developers.google.com/identity/protocols/oauth2/cross-client-identity))

Each device authorizes the **same Google account** independently. Verify that files and required app metadata are accessible across SPino's Android/iOS clients; consent reuse alone does not prove every file-discovery behavior. Store a versioned media binding to the existing notebook UUID, without tokens, and validate the remote notebook identity before transfers. The current OS URI/bookmark is not a Drive OAuth grant. If notebook JSON later moves to REST access, explicitly open that exact file through Google's supported Picker flow and verify its notebook identity. ([Desktop/mobile Picker](https://developers.google.com/workspace/drive/picker/guides/desktop-mobile-picker), [current notebook binding](/Users/migue/Source/spino/src/companion/cloud-sync.js:40))

The notebook and media can intentionally use different providers. Show the selected media account and reconnect errors; an inaccessible folder must not silently create a second empty library. A QR code remains a locator, never authorization. Different people require Drive sharing permissions plus app access, or a managed membership system; a file ID alone grants nothing. Use supported native/system-browser authorization and secure token storage. ([Drive sharing](https://developers.google.com/workspace/drive/api/guides/manage-sharing), [native OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [security practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices))

## Preserve recordings through conflicts, deletion and migration

A mutable manifest alone cannot prevent concurrent writers losing updates. The prototype must prove authoritative conditional revisions or use immutable metadata operations with deterministic reconciliation. Reuse SPino's three-way merge principles: independent changes combine, while two unequal title edits retain both candidates for resolution. Avoid device-clock precedence. This concurrency design remains a technical gate, rather than a verified Drive feature. ([Existing merge](/Users/migue/Source/spino/src/companion/cloud-merge.js:14))

Distinguish removing a local download from deleting everywhere. Global deletion needs durable tombstones so an old offline device cannot resurrect a take; deletion versus concurrent rename needs an explicit policy and recovery retention. Initially avoid automatic permanent garbage collection. Disconnecting preserves originals and remote files; changing accounts must fence outstanding transfers so late responses cannot publish to another notebook.

Existing recordings have no notebook scope, and restoring a notebook deliberately preserves them. Therefore, **never upload every local recording to the currently connected notebook**. Keep drafts and original bytes, preserve IDs, migrate one take at a time with a journal and verified copies, and let users select existing recordings whose notebook association is known. Leave unmatched recordings local. Legacy notebook clients must remain safe; use a separate versioned media manifest rather than relying on unknown fields surviving old JSON writers. ([Restore/export](/Users/migue/Source/spino/src/companion/store.js:70), [media invariants](/Users/migue/Source/spino/tests/media.browser.test.js:16), [format policy](/Users/migue/Source/spino/docs/backup-formats.md))

## Prove the native path before enabling migration

First, prototype Google authorization and streaming on two disposable native installations with a synthetic notebook. Gate success on same-account discovery, verified byte hashes and actual playback on device B, including a two-minute recording and a near-limit transfer fixture. Test interrupted uploads, app termination/restart, expired authorization, quota exhaustion, account mismatch and format compatibility. Browser evidence remains separately labeled. Any review APK must replace the installed app, preserve its data, launch and reach the foreground. ([Repository handoff requirements](/Users/migue/Source/spino/AGENTS.md))

Next, implement the manifest/operation contract and local queue behind synthetic transports; pass offline additions, concurrent renames, deletion/reconnection, corrupt downloads and crash recovery without duplicate takes or lost originals. Then integrate Drive, exercise both target platforms and verify existing IDs, PDFs and annotations remain unchanged. Enable optional migration only after these gates pass. No product code, accounts, cloud resources or personal data were changed by this research.

The provider preference is settled: personal Google Drive with no additional SPino subscription. Remaining decisions are whether the scope includes different people, which platforms must ship first, the exact Google authorization experience, and whether privacy requires application end-to-end encryption with key recovery. Wi-Fi policy, offline retention and deletion recovery also need explicit defaults. Resolve these before rollout; they do not prevent the small native feasibility test, and they are proposed decisions rather than approved requirements.
